# OpenAIのDecisions APIがGAに：分類・分岐をResponses APIと分けて設計する

YAMASHI TECH AI Editorial Desk | News | AI / ML / AI Agents / DevTools

[掲載ページ](https://yamashi-tech.com/articles/news-openai-decisions-api-general-availability) · [原稿データ](../articles/news-openai-decisions-api-general-availability.json)

公開: 2026-10-24 / 更新: 2026-10-24 / 確認: 2026-10-24

OpenAIはDecisions APIを一般提供へ移行した。確率・選択・スコアの3形式で、生成回答ではなくアプリ内の限定された判断を返す。GAで増えたJSON入力、画像指示、最大400問、GPT-Live連携を、導入前の評価条件とともに整理する。

## 要点：生成より前の小さな判断を、専用の返り値にする

OpenAIは2026年10月22日、GPT-6 Lunaを使うDecisions APIを一般提供（GA）に移した。これは長い文章を生成するためのAPIではなく、入力を分類する、次の処理を選ぶ、定義済みの尺度で評価するといった、答えの形があらかじめ限られた判断を返すためのAPIだ。

既にResponses APIで同種の判定を実装しているチームは、まず判断を一つに切り出せるかを見るとよい。人へ確認を回すか、再試行するか、問い合わせをどのキューへ送るかのように、許される出力と後続処理が明確な場所が候補になる。自由文の回答や根拠説明そのものが成果物なら、Decisions APIだけで置き換える対象ではない。

- Fact：GAの対象モデルはGPT-6 Lunaで、専用のDecisions endpointを使う。
- Fact：返り値の形式はpredicate、choice、scoreの3種類である。
- Inference：生成と判定を分けると、後続処理の許容範囲と失敗時の確認条件をコード上で明確にしやすい。

## GAで追加・拡張されたこと

公式発表とAPI Changelogによると、公開ベータからGAまでに、再利用する文脈向けのprompt caching、個々の質問指示への画像、構造化データを直接渡すinput_json、GPT-Liveとのネイティブ連携が加わった。1リクエストに含められる質問は200件から400件へ増えた。

この400件は、すべての業務を一度に自動化できるという意味ではない。各質問には許される選択肢や評価尺度を定める必要があり、まとめた質問のどれかが曖昧なら、バッチ全体の扱い方も事前に決めておく必要がある。

公式発表で示された、Decisions APIの回答形式

| 形式 | 返すもの | 向く判断の例 |
| --- | --- | --- |
| predicate | 条件が真である確率（0から1） | 画像に損傷が見えるか |
| choice | 定義済み選択肢の一つと確率・confidence | 続行、再試行、確認依頼のどれにするか |
| score | 順序づけた尺度の確率加重平均 | 損傷の重大度を段階で評価する |

## 対象読者：ルーティングやガードを生成本体から分けたいチーム

通知の仕分け、ツール実行前の確認、ライブ会話中の分岐のように、低遅延で同じ型の判断を繰り返すアプリケーションが主な対象になる。公式のGPT-Live例では、音声入力のtranscript deltaを受け、アバター表情をchoiceとして選び、Liveがdecision.eventを返す構成を示している。

Recommendation：最初の候補は、誤っても安全に戻せる判断に限定する。choiceの結果をそのまま外部APIの書き込みへつなげず、許可リスト、確信度の閾値、人へのエスカレーション、同じ入力を再実行しないための識別子を後続側に置く。

## 導入前に評価すべき条件

公式発表には、特定顧客がResponses APIより速い、または低コストだったという数値がある。しかし、入力件数、プロンプト、リージョン、失敗の定義、ベースライン、測定期間は各事例で異なる。これらを一般的な性能保証として読むことはできない。

Recommendation：本番データを渡す前に、匿名化または合成した入力で、正解率だけでなく、誤判定の種類、confidenceが低いときの振る舞い、p95遅延、キャッシュ有無の料金、タイムアウトとリトライを記録する。判定結果を採用しない基準を先に決めれば、速度だけを理由に危険な自動化へ広がるのを防げる。

実行していない、後続処理の安全境界を示す概念例

```text
choice が "execute" でも、confidence が閾値未満なら人へ確認する
choice が許可リスト外なら停止する
外部書き込みは、別の認可と冪等キーを満たすときだけ実行する
API障害・形式不正・タイムアウトは自動承認ではなく保留にする
```

## 価格、リージョン、データ管理は別々に確認する

公式発表時点の価格は、入力100万トークン当たり0.10ドル、キャッシュ済み入力は0.01ドルで、出力トークン料金はないとされる。一方、30分・12時間のキャッシュ書き込み価格は別途ガイドを参照する仕様だ。単価だけで月額を決めず、入力長、キャッシュヒット率、リクエスト数、書き込み価格を同じ前提で見積もる必要がある。

Fact：公式発表はUS/EUのregional processingと、対象顧客向けのZero Data Retentionに触れている。これらは自動的に全組織へ適用されるという記載ではない。自社の対象可否、設定手順、保存・監査の要件は、導入時点のデータ管理文書で確認する。

## 次に確認する条件

導入候補の判断を一つ選び、許される出力、保留条件、人による確認先を定義できたときに、小さな評価を始める。逆に、結果の誤りがそのまま支払い、削除、公開、権限変更へつながり、確認経路も用意できないなら、GAという提供状況だけを理由に組み込む段階ではない。

今回確認したのは2026年10月24日である。料金、利用可能なリージョン、モデル、キャッシュ条件、データ管理機能は変更され得るため、実装前と本番投入前に公式ドキュメントを再確認する。

## 制約と未検証範囲

- 速度、精度、コストに関する顧客事例は各社が示した条件での報告であり、編集部は再現していない。別の入力分布、地域、負荷、評価指標で同じ結果になるとは限らない。
- 本記事ではAPIリクエスト、Playground、課金、組織設定、Zero Data Retentionの有効化を行っていない。実際の利用可否、リージョン、価格、データ管理条件は導入時に公式ドキュメントと契約条件を再確認する必要がある。
- 確率・confidenceは業務上の正しさや安全性を保証しない。不可逆な処理や高リスク判断には、人による確認と失敗時の停止経路が必要である。
