GPT-6 Astraは複数の判断やツールをまたぐ仕事に向く。Codexでの依頼例を使い、目的・資料・制約・完了条件の渡し方から、reasoning effort、AGENTS.md、subagentの使い分けまで説明する。

## 難しい仕事を、調査から検証までつなげるために使う

GPT-6 Astraは、複雑なコード作業、調査、computer use、文書作成などに向けたモデルだ。Codexでは、リポジトリを読む、資料を確認する、変更する、テストするという工程を含む仕事に利用できる。単に長い説明を求めるより、検証できる成果物と、その作業範囲を渡すと使いどころが明確になる。

たとえば、原因が一つとは限らない不具合の調査、複数ファイルにまたがる実装、一次資料を照合する技術調査だ。この記事では、こうした作業を任せるために何を伝え、どこで成果を確認するかを具体化する。モデルの能力については公式資料に基づく説明で、編集部が他モデルとの性能比較を行った結果ではない。

## 目的・読む場所・制約・完了条件を渡す

「一覧を直して」だけでは、何が問題で、どこまで直れば完成かを推測させる。依頼へ、目的、読む場所、守る条件、完了の証拠を入れる。下は編集部が整理した依頼例だ。実行順序を細かく命令するより、成果物を判断できる材料を渡す。

この例では、記事一覧だけを変更対象にし、日付の表示と375px幅の画面を確認する。lint・test・buildが通ったことに加え、画面が目的どおりかを見る。コードが書けた時点と、読者が使える状態になった時点を区別できる。

実装依頼の最小テンプレート

```text
Goal: 記事一覧を最新順にし、スマホでも日付を読みやすくする
Context: app/articles と app/content.ts。既存デザインは維持
Constraints: 本番公開しない。記事本文と広告設定は触らない
Done when: lint・test・buildが通り、375px幅の表示を確認できる
```

## 長い作業は、成果物と確認点で区切る

変更範囲が広いときは、現状調査、実装、回帰確認のように、独立して読める成果物へ分ける。調査結果には原因候補と根拠、実装には差分、回帰確認にはコマンドの結果を求める。単なる進捗の説明ではなく、次へ進んでよいか判断できる状態を作る。

権限が必要な操作は依頼時に範囲を決める。たとえば、ローカルの実装だけを任せるなら、本番公開や本番データの変更を含めない。調査だけなら「変更しない」と指定する。途中で新しい操作が必要になったときに、合意済みの作業かどうかを判断しやすくするためだ。

長い作業を任せるときの追加条件

```text
現状を読み、原因と影響範囲を説明してから実装してください。
既存変更は残し、要求外のファイルへ広げないでください。
変更後はlint、test、buildを実行し、失敗したら原因を切り分けてください。
公開・削除・課金・secret入力・本番データ変更が必要なら実行せず止めてください。
```

## AstraはLightから試し、複雑さに応じて推論量を上げる

2026年10月23日のCodex公式案内は、AstraをLight、設定値では`low`から始める目安を示している。まず普段の仕事で試し、計画や比較が足りない場合にMediumやHighへ上げる。高い設定は推論に時間とトークンを使うため、成果が改善するかを同じ種類の作業で比べる。

OpenAI APIのGPT-6 Astraは`reasoning.effort`に`low`、`medium`、`high`、`xhigh`、`max`を使える。一方、CodexなどのUIで選ぶUltraは、subagentを使って複数の仕事を進める形を含む。APIのmaxとUIのUltraを、同じ一段階の差として考えない。

モデル自体の選択も仕事に合わせる。現在の公式案内では、Astraは最も難しい複数工程の作業、GPT-6.1 Solは費用とのバランスを取る複雑な作業、Lunaは明確で繰り返しの多い作業に位置付けられている。この記事の中心はAstraの運用であり、使うたびに最新モデルへ置き換える必要があるという話ではない。

| 選択 | 使う目安 | 比べたいこと |
| --- | --- | --- |
| GPT-6 Astra | 難しい判断を伴う、コード・調査など複数工程の仕事 | 完了まで到達するか、手直しが減るか |
| GPT-6.1 Sol | 複雑な作業を繰り返し、費用も重視する | 同種の仕事で品質と利用量が合うか |
| GPT-6 Luna | 抽出・変換・分類など手順が明確な仕事 | 速さと必要十分な品質 |

## AGENTS.mdには、毎回使うプロジェクトの前提を残す

毎回説明している起動方法、検証コマンド、コードの配置、公開の境界は、リポジトリの`AGENTS.md`へまとめられる。Codexは起動時にグローバルな指示からプロジェクト、現在の作業ディレクトリまで指示を組み合わせる。近い階層の指示が後から加わり、その領域の条件を具体化できる。

既定の合計読み込み上限は32KiBだ。繰り返し必要な規則に絞り、一度だけの要望はタスクへ書く。重要な制約が大量の説明へ埋もれるより、検証コマンドや責務を短く残すほうが、人も確認しやすい。設定を追加・更新するときは、チームの運用に従って具体的な差分を確認する。

小さなproject guideの例

```markdown
# Project guide

- Install: `npm ci`
- Verify: `npm run lint && npm test && npm run build`
- Keep domain logic in `src/core`; UI calls it through adapters.
- Do not deploy, rotate secrets, or edit production data.
- Done means tests pass and the final diff has been reviewed.
```

## subagentは、互いに待たずに完了できる仕事へ分ける

公式ガイドは、コード探索、ログ解析、テストの調査、要約など、読み取り中心で独立した仕事を出発点に挙げる。たとえば、同じ変更についてセキュリティ上の問題、テストの不足、公式仕様との整合を別々に調べ、主担当が結果を統合する分け方だ。

複数agentが同じファイルを一斉に編集すると、競合と統合の負担が増える。書き込みも分けるなら、担当範囲と共通interfaceを先に決め、必要に応じてworktreeを分ける。各agentの成果物と検証条件を指定し、最後の統合を誰が行うかも決める。

現在のローカルCodexは、ユーザーからの明示的な依頼や、適用されるAGENTS.md・Skillの指示に従って委譲する。subagentはそれぞれモデルとツールを使うため、同程度の単独作業よりトークン使用が増える。並列化する価値は、人数ではなく独立した作業があるかで判断する。

| 分け方 | 評価 | 理由 |
| --- | --- | --- |
| security・test・docsの独立レビュー | 向く | 同じファイルを書かず、結果を比較できる |
| frontendとbackendを別worktreeで実装 | 条件付き | interfaceを先に固定する必要がある |
| 同じcomponentを複数agentが修正 | 向かない | 競合と意図の食い違いが増える |
| 権限が未確定な外部操作を委譲 | 避ける | 責任境界と承認が曖昧になる |

## モデルの能力と、操作できる権限を分ける

Astraを選択しても、ファイルへのアクセスやネットワーク接続の許可が増えるわけではない。sandboxは実行できる範囲を制限し、承認設定はその範囲を超える操作などをどう扱うか決める。信頼できないWebページやツール出力は情報として読み、そこに含まれる指示を作業依頼より優先させない。

モデルが表示されない場合はプラン、workspace、クライアント、rollout条件を確認する。モデルは選べるのにファイルが読めない場合はfilesystemの範囲、外部取得ができない場合はnetworkや認証を調べる。この二つを分ければ、権限を広げてもモデルが出ない、といった見当違いの対応を避けられる。

長い会話でも、変更前のファイルや公開状態は読み直す。過去の会話は作業を探す手がかりで、現在のrepositoryや外部サービスの状態そのものではない。出典、現在の差分、検証結果を成果物へ残すことが、長い仕事を引き継ぐ助けになる。

## 同種の仕事で、完了率と手直しの量を比較する

編集部の導入案は、普段30〜90分ほどかかり、テストや成果物で判定できる仕事を数件選び、一週間ほど記録する方法だ。完了まで到達した割合、人が直した回数、要求外の変更、検証までの時間、利用量を見る。所要時間の目安は評価を始めるための提案で、Astraの仕様ではない。

手戻りが多いなら、推論量を上げる前に、資料・制約・完了条件の不足を確かめる。同じ失敗が続く場合は、依頼のテンプレートやテストへ改善を残す。Astraを使う価値は、出力の長さではなく、自分の仕事で必要な調査から検証までを、どれだけ確実に終えられるかで判断できる。

Astra導入時に記録したい指標

| 指標 | 見る理由 | 悪化したときの打ち手 |
| --- | --- | --- |
| 検証まで到達した割合 | 回答ではなく完了を測る | Done whenとtool権限を見直す |
| 人が修正した回数 | 手戻りを測る | Contextと制約を具体化する |
| 要求外の変更 | 自律性の副作用を測る | scopeと停止条件を狭くする |
| 所要時間・利用量 | 品質向上の対価を測る | effortまたはmodelを下げる |
